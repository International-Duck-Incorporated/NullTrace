# NullTrace CI review — 2026-10-26

Scope: `main` @ `7f2dde9`, the whole of `.gitlab-ci.yml`, the build script it
invokes, and the artifacts actually published for `v2.1.0`.

Method: cloned the repository and read the pipeline end to end; downloaded the
released `v2.1.0` jars and checksum assets from the GitLab package registry and
audited them; ran the old pipeline's shell snippets against real files in a
scratch directory to reproduce their behaviour; ran the new checks against the
real repository and against deliberately broken fixtures.

Not done here: a live pipeline run (the namespace has no compute minutes — the
first finding — and this environment has neither Docker nor a JDK 25, so Gradle
itself never ran). Every claim below is either read from the repository, read from
the published artifacts, or reproduced with the exact commands quoted.

Ranked by what it costs if left alone.

---

## F1 — The pipeline is dark: every job fails before it starts · P0

Pipeline [#2957405437](https://gitlab.com/international-duck-incorporated/NullTrace/-/pipelines/2957405437)
for `main` @ `7f2dde9` ("1 week ago") is red in every job, and no job has a trace:

> `build: [1.21.11]`, `build: [26.1]`, `build: [26.2]`, `build: [26.3]`,
> `policy_tests: [1.21.11]`, `policy_tests: [26.3]`, `adversarial_fixture`,
> `proxy_probe_harness`, `security_audit` — **"No more compute minutes available"**

So the newest commit on `main` has never been compiled, and a tag pushed today
would fail at the first Gradle job. Nothing in the repository currently proves
that `2.1.1` builds.

That message is a namespace quota condition, not a code defect; no YAML change
makes it go away. What YAML can do is stop *wasting* the minutes that are left:

| | old pipeline | new pipeline |
| --- | --- | --- |
| jobs per feature-branch push | 9 | 5 |
| jobs that run Gradle | 8 | 2 |
| jobs per tag / `main` push | 9 | 10 (6 Gradle, 4 cheap) |
| fails in seconds on a metadata typo | no | yes (`preflight`) |
| superseded pipelines cancelled | no | yes (`auto_cancel`) |
| duplicate branch pipeline next to an MR | created | suppressed |

**Fix.** `preflight` (pure Python, no Gradle) runs first and blocks the builds;
the four-target matrix is limited to `main` and tags; per-target Gradle caches
with `pull` policy on the test jobs; the dependency report moved into the 26.3
build (it used to pay for a whole extra Gradle start); the jar audit is Python.
`auto_cancel.on_new_commit: interruptible` stops paying for pipelines nobody is
waiting for. A self-hosted runner is documented as the durable answer:
[`runbook.md`](runbook.md#self-hosted-runner).

## F2 — The next release would ship checksum files that fail verification · P0

The build job wrote checksums like this:

```bash
for JAR in release/*.jar; do sha256sum "$JAR" > "$JAR.sha256"; done
```

`$JAR` is `release/nulltrace-26.3+v2.1.0.jar`, so the sidecar contains that path:

```
fef2…21e4  release/nulltrace-26.3+v2.1.0.jar
```

Reproduced with the current snippet, then verified the way a user would:

```
$ sha256sum -c nulltrace-26.3+v2.1.0.jar.sha256
sha256sum: release/nulltrace-26.3+v2.1.0.jar: No such file or directory
release/nulltrace-26.3+v2.1.0.jar: FAILED open or read
```

`security_audit`'s own `sha256sum --check "$JAR.sha256"` passes only because it
runs from the project root, where `release/` exists. The check is green on a file
that is broken for every user.

The published `v2.1.0` sidecars are *correct* (bare file name; the hash matches
the 521 778-byte jar I downloaded), so this is a regression introduced by the
current pipeline, not a shipped defect — it would have shipped with the next tag.

**Fix.** `tools/ci/gen_sums.py` writes bare names with LF endings, generates the
`SHA256SUMS` bundle, and `--verify` re-checks everything from inside `release/`.
The self-test asserts bare names, LF, and that `sha256sum -c` succeeds, and that
`--verify` rejects the old `release/`-prefixed form.

## F3 — A tag could publish an untested jar · P0

```yaml
publish:
  needs:
    - job: build        # ← the only dependency
```

In GitLab, a job with `needs` no longer waits for earlier stages. `publish` was
therefore eligible to start as soon as the four build jobs had uploaded artifacts,
whatever `policy_tests`, `proxy_probe_harness`, `security_audit` and
`release_tag_guard` were doing. A red test would turn the pipeline red *after* the
release had already been created and its assets linked.

The tag guard itself was sound (it compares `mod_version` with the tag), but it
sat in the `security` stage with `needs: []` and nothing depended on it.

**Fix.** The tag check moved into `preflight`, which runs in the first stage, so a
mis-tagged release fails in seconds. `publish` now needs `preflight`,
`policy_tests_matrix`, `policy_tests_smoke`, `proxy_probe_harness`, `jar_audit`
and `build_matrix`. It also has `resource_group: release`, so two tag pipelines
cannot interleave uploads.

## F4 — 2.1.1 exists everywhere except in a tag · P1

| Source | Says |
| --- | --- |
| `gradle.properties` | `mod_version=2.1.1` |
| `CHANGELOG.md` | `## [2.1.1] - 2026-10-17`, including a **Security** section |
| Tags | `v2.0.0`, `v2.1.0` only |
| Latest release | `v2.1.0`, 3 weeks ago |
| CurseForge / website | 2.1.0 |

The `[2.1.1]` security section says the offline ("cracked") account path was
removed, redirect handling fixed, tokens encrypted at rest, and account HTTP
routed through the configured proxy. The published `2.1.0` jar still contains
`net/nulltrace/mod/accounts/CrackedAccount.class` and
`net/nulltrace/mod/config/AddCrackedAccountScreen.class` (both listed in the jar's
`Fabric-Loom-Client-Only-Entries` manifest attribute), so users are running the
code the changelog says was removed.

`2.1.1` is a security release that is written down but not shipped.

**Fix.** Nothing automatic — this needs a human with minutes or a runner. The
procedure is in [`runbook.md`](runbook.md#releasing); `preflight --tag v2.1.1`
verifies the tree is taggable. Added defence: `preflight` fails when a tag and
`mod_version` disagree, and warns when `CHANGELOG.md` has no section for the
current version.

## F5 — Feature branches and merge requests had no pipeline · P1

```yaml
workflow:
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    - when: never
```

Anything that is not a tag or a push to `main` gets no pipeline. The new linter
reports this for the old file as `pipeline is not created (workflow rules match
'never')` for both the branch and merge-request scenarios. Contributions are
unverified until they land on `main`, and an MR shows no checks at all.

**Fix.** `merge_request_event` and non-default branches now get a reduced
pipeline (`build_smoke` + `policy_tests_smoke` + the cheap jobs). The duplicate
branch pipeline that GitLab would create next to an MR is suppressed with
`$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS → never`.

## F6 — Cache and job design multiplied the Gradle cost · P1

```yaml
cache:
  key: "gradle-${CI_COMMIT_REF_SLUG}"
```

One cache key per branch, written by four matrix jobs in parallel (they race to
upload the same key, and the last writer wins), and read by jobs whose dependencies
differ. `security_audit` then paid for another Gradle start to produce a dependency
report, in a stage whose only real job was inspecting a zip.

**Fix.** `key: gradle-$MC_VERSION` with `policy: pull-push` on builds and
`policy: pull` on tests; the dependency report is produced by the 26.3 build job
where Gradle is already warm; the audit is `python:3.12-alpine` with no cache.

## F7 — Test results were discarded · P2

`./gradlew :26.3:test` printed to the job log and nothing else. No
`artifacts:reports:junit`, so GitLab's test report tab was empty and a failure
meant scrolling a 3 000-line log. **Fixed**: both test jobs publish
`versions/$MC_VERSION/build/test-results/test/*.xml` with `when: always`.

## F8 — `SHA256SUMS` and the provenance manifest were never produced by CI · P2

The `v2.1.0` release notes say "SHA256SUMS and individual SHA-256 checksum files
are attached", and the asset exists in the package registry — but the pipeline
never generated it:

```
$ git log -S'SHA256SUMS' --oneline -- .gitlab-ci.yml
(no output)
```

The next release would quietly have lost the asset its own notes promise.
`release-manifest.json` (commit, pipeline, per-file hashes, target ranges) was
never produced at all. **Fixed**: `gen_sums.py` writes both, `publish` uploads and
links them.

## F9 — The `security_audit` jar inspection was close to cosmetic · P2

It ran `./gradlew :26.3:dependencies` (a full Gradle start) and then:

- `grep -E '(^|/)accessToken$|(^|/)refreshToken$'` on a **file listing** — those
  are never entry names, so this could not match anything;
- a `sed`-based refmap check (the one genuinely useful assertion, kept);
- `sha256sum --check` on a checksum whose format was itself broken (F2).

It did not check that the jar's version matched the tag (only `publish` did), that
entrypoint classes exist, that class files match `depends.java`, that nested JiJ
jars load, that mixin entries have classes, that JSON resources parse, or that the
LICENSE travels with the binary.

**Fix.** `tools/ci/inspect_jar.py` runs 18 checks in ~0.2 s with no JDK. Verified
against the real `v2.1.0` jar (18/18 pass) and against five mutated copies; each
mutation trips the intended check. `tools/ci/selftest.py` keeps that true.

## F10 — Release API errors were swallowed · P2

```bash
curl … --request POST … "$RELEASE_URL" || true
curl … --request POST … "$RELEASE_URL/$VERSION/assets/links" || true
```

A failed release creation or a failed asset link left the job green, producing a
release page with no assets. **Fixed**: HTTP status is captured; `2xx` and `409`
(already exists) are accepted, anything else fails the job with the response body,
and uploads use `--retry 3 --retry-connrefused`.

## F11 — Smaller things, all fixed

| Item | Before | Now |
| --- | --- | --- |
| `GIT_DEPTH` | `0` — full clone in every job | `20` |
| runner flakes | no retry | `retry` on `runner_system_failure`, `stuck_or_timeout_failure` |
| hung jobs | no timeouts | `default.timeout: 45m` |
| job overhead | no `interruptible` | `interruptible: true` everywhere |
| Pages | `fabric.mod.json` homepage points at a Pages URL that nothing in this repo publishes | optional manual `pages` job |
| CI definition | only discoverable by pushing | `tools/ci/lint_gitlab_ci.py` lints it and simulates five scenarios locally |

## F12 — Not changed, needs your call · P3

- **Images are floating tags** (`eclipse-temurin:25-jdk`, `python:3.12-alpine`,
  `alpine:3.22`). Pinning by digest makes a rebuild reproducible. I did not pin
  them because I cannot resolve digests from here and a wrong digest is a hard
  pipeline failure.
- **`publishing.artifactId` uses `nulltrace-$minecraft_version`**, while the jar
  name uses `version_suffix`. For `26.1` the artifact id is `nulltrace-26.1.2`
  but the jar is `nulltrace-26.1-26.1.2+…`. Harmless today (nothing consumes it),
  confusing tomorrow.
- **The marketing site is stale and unconnected to releases**: it advertises
  `2.1.0` and renders the release-note heading literally (`**## NullTrace 2.1.0**`).
  If it consumed `release-manifest.json`, this would not happen.
