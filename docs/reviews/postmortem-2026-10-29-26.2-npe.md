# Postmortem — 2.2.0 could not connect on Minecraft 26.2

**Severity:** release blocker for one target. **Affected:** `nulltrace-26.2+v2.2.0.jar`. **Fixed:**
2.2.1. **Reported by:** a user's Prism Launcher log (Windows 11, Fabric Loader 0.19.5, 26.2).

## Symptom

Every outgoing packet threw before it reached the wire:

```
[Server Pinger #1/ERROR]: Failed to ping server play.enchantmc.com:25565
java.lang.NullPointerException: Cannot invoke
  "java.util.concurrent.atomic.AtomicBoolean.compareAndSet(boolean, boolean)"
  because "this.nulltrace$logged" is null
	at net.minecraft.network.Connection.handler$bne000$nulltrace$onSend(Connection.java:2921)
	at net.minecraft.network.Connection.send(Connection.java)
	at net.minecraft.client.multiplayer.ServerStatusPinger.pingServer(ServerStatusPinger.java:173)
```

and, on a connection attempt, the same trace from `ConnectScreen$1.run` →
`Couldn't connect to server`. The server list showed every entry as unreachable and no server
could be joined. Everything else — fonts, mods, the privacy warning screen — worked, which is what
made it look like a networking problem rather than a mod bug.

## Root cause

`ClientConnectionMixin` (`@Mixin(Connection.class)`) declared its log-once guard as a `@Unique`
**instance** field with a field initialiser:

```java
@Unique
private final AtomicBoolean nulltrace$logged = new AtomicBoolean(false);
...
if (nulltrace$logged.compareAndSet(false, true)) { ... }   // called from Connection#send
```

Mixin implements a mixin's instance field initialisers by merging them into the target class's
constructors. On Minecraft 26.2 that merge did not happen for `net.minecraft.network.Connection`:
the field was added to the class, but no constructor ever assigned it. The field was therefore
`null` on every instance, and because `Connection#send` calls `compareAndSet` unconditionally,
every send threw.

Verified by dumping the transformed class with `-Dmixin.debug.export=true` and reading the
bytecode of the merged `Connection`:

| Evidence | Result |
| --- | --- |
| `javap` field list of merged `Connection` | `private final AtomicBoolean nulltrace$logged;` — present |
| any `putfield nulltrace$logged` in the class (constructors, methods) | **none** |
| `putstatic nulltrace$sending` (a `@Unique` **static** field in the same mixin) | present in `<clinit>` |

So the static initialiser merged and the instance one did not. That is why the class looked fine in
review and why the same source works on 1.21.11 (the initialiser merges there — the 2026-10-28
runtime test connected to a world with this exact code).

Why it was invisible to the test suite: the field is only touched from `Connection#send`, which no
unit test exercises (no Minecraft runtime), and the 1.21.11 runtime test that *did* exercise it ran
on a target where the merge works.

## Fix

The guard is now created on first use, so nothing depends on the merge:

```java
@Unique
private volatile AtomicBoolean nulltrace$logged;

@Unique
private AtomicBoolean nulltrace$logOnce() {
    AtomicBoolean flag = nulltrace$logged;
    if (flag == null) {
        flag = new AtomicBoolean(false);
        nulltrace$logged = flag;
    }
    return flag;
}
```

Two Netty threads racing here can each create an instance; the only consequence is that a debug
line prints at most twice, which is acceptable for a log-once guard and is stated in the comment.

Every other `@Unique` member in the same class was audited at the same time:
`nulltrace$pipelineHandlerInstalled` (boolean, default `false` is the correct value),
`nulltrace$sending` (static `ThreadLocal`, merged into `<clinit>`), and the registration-constructor
cache (static, also `<clinit>`).

## Verification

Reproduced and fixed on 26.2 in this environment (Linux, Xvfb + llvmpipe, JDK 25.0.5, Fabric Loader
0.19.5), driving the client with `--quickPlayMultiplayer` against a local TCP listener:

| Build | Result |
| --- | --- |
| 2.2.0 (unfixed) | privacy warning screen → **Protect & connect** → `NullPointerException … "this.nulltrace$logged" is null` at `Connection.send`, connection refused |
| 2.2.1 (fixed) | privacy warning screen → **Protect & connect** → connection established, listener received `17 bytes` (handshake + login start), **no exception** |

The client was then left waiting for a reply from the fake endpoint, i.e. it had gone as far as
26.2 lets a client go without a real server. Pinging uses the same `Connection#send`, so the ping
path is fixed by the same change.

Also run after the change: `:1.21.11:test` and `:26.3:test` (113 tests each), compile for all four
targets, `tests/proxy` 65/65, `tests/vault` 26/26, and the full `preflight` suite.

## Prevention

`tools/ci/check_sources.py` gains **SRC010**: a `@Unique` instance field in a mixin may not depend
on its initialiser.

* flagged — `= new AtomicBoolean(false)`, `= SomeConstant.VALUE`, `= 42`, `= true`
* allowed — no initialiser, or `= null / false / 0` (identical to the JVM default, so a lost
  initialiser changes nothing), and any `@Unique` **static** field (merged into `<clinit>`, which
  demonstrably works)

`tools/ci/selftest.py` has three cases for it (bad instance initialiser fails, JVM-default passes,
static initialiser passes), so the check is itself tested.

This is a source-level rule, not a bytecode proof, and that is a deliberate limit: it encodes the
one invariant that failed, costs a second to run, and needs no class-file parsing. The stronger
version — verify after transformation that every `@Unique` instance field of every mixin is
assigned somewhere or is null-safe — belongs in the jar audit and is filed as a follow-up.

## What this says about the test strategy

The 2026-10-28 runtime test proved "the client runs and the protections fire" on **1.21.11**. This
bug was in a code path that test did exercise, but on a *different target*, where Mixin behaved
differently. The gap was not "we never launched the client"; it was "we launched one of four
targets and generalised". The fix for that is a smoke run per target before a release, which needs a
machine that can host a client (this sandbox can, headless) and is now the first item written into
`docs/devops/runbook.md`'s release checklist.
